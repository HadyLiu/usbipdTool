# 发布

GitHub Actions 工作流见 [`.github/workflows/ci.yml`](../.github/workflows/ci.yml)。当前版本号以 `Cargo.toml` 为准，为 **0.1.2**。

## 触发方式

推送 `main` / `master` 或提交 Pull Request 时，会启动**一次**串行任务，依次完成：

1. 按 `docker/Dockerfile` 与 `.dockerignore` 的内容指纹解析工具链镜像标签（`toolchain-<指纹>`），尝试从 GHCR **拉取**已有编译镜像；只有该标签不存在时才在 runner 上执行 `script/build-image.sh`。来自主分支的推送在首次构建（缓存未命中）后会发布这个不可变标签，供以后运行复用。外部仓库的 Fork PR 不会登录或发布，拉不到镜像时在本地构建工具链。
2. 用 `./script/build.sh` **始终重新编译本仓库源码**（测试并交叉编译）。临时 runner 每次可能会**下载**已有工具链镜像，但在指纹未变时**不会重建**该镜像。
3. 上传 `dist/UsbipdTool.exe` 及其 SHA256。
4. 仅当这是指向主分支的推送，并且仓库里存在与 `Cargo.toml` 版本一致的标签（例如 `v0.1.2`），且该标签**精确指向本次构建的提交**时，才创建或更新对应 GitHub Release，并把该工具链镜像额外打上版本号与 `latest` 标签推送到 GHCR。

没有匹配的版本标签时，只保留构建产物，不会发布历史版本。同一分支上的运行串行执行。**单独推送标签不会触发工作流。** Pull Request 会做编译验证，但不会发布。

发布检查会再次拉取标签，并核验 `HEAD` 等于本次构建的 `GITHUB_SHA`。标签名称必须是 `v` 加上 Cargo 版本（如 `v0.1.2`），且 `git rev-parse refs/tags/v0.1.2^{commit}` 必须等于该 SHA。不使用「仓库里最新的任意 tag」。

## 如何把代码和标签一起推送

要发布 0.1.2，请让 `v0.1.2` 在工作流检查时已经指向即将构建的那个提交。推荐一次原子推送分支和标签：

```bash
git tag v0.1.2
git push --atomic origin main v0.1.2
```

如果先只推 `main`，等工作流开始后再补打标签，这次运行可能检查不到标签，因而只上传产物、不发布 Release。单独 `git push origin v0.1.2` 也不会启动构建。

同一提交重复发布时，若 Release 说明里已包含本次构建 SHA 的标记，工作流会跳过重复发布。

## 拉取构建镜像

镜像名为 `ghcr.io/<owner>/<repo>`（自动转小写）。内容指纹标签形如 `toolchain-<16 位十六进制>`，在主分支首次构建该 Dockerfile 时发布，之后的工作流运行直接拉取。版本发布还会打上版本号（如 `0.1.2`）和 `latest`。这些都是 Rust + MinGW 的**交叉编译环境**，不是可运行的 Windows 界面；Windows 程序请到 GitHub Release 下载。

```bash
echo "$GITHUB_TOKEN" | docker login ghcr.io -u USERNAME --password-stdin
docker pull ghcr.io/<owner>/<repo>:0.1.2
```

本地编译请使用 [编译](编译.md) 中的 `./script/build.sh`，不需要依赖 GitHub Actions。
